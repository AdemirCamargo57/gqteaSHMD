# Release 0.1.0: design

Status: written 2026-11-25; the design was approved by the owner in conversation, section by section, on 2026-11-25; this written spec awaits the owner's review. Branch `feat/release-0.1.0` (from `main` `82e7d35`).

## 0. Owner decisions (2026-11-25)

Taken by multiple choice; the owner took the recommended option each time.

1. **Audience:** the release is for ourselves, reproducibly. Version 0.1.0, a git tag, a GitHub Release with notes, a build stamp so that a normal (non-editable) install records its commit, and a check that a clean install from the release commit runs the workflow. Installed from the repository's release; **no PyPI, no conda-forge**.
2. **Gate:** CI green on the release commit, the full suite here with SHARC and ORCA, and a clean install (a fresh environment, the built wheel, not editable) running a small water project through the analysis, with provenance recording the release version and commit.
3. **Environment pinning:** an exact lock file of the tested environment (`conda list --explicit`, linux-64) is part of the release; `environment.yml` stays the loose development spec.
4. **Scope:** release only. No behaviour change; every existing project stays up to date. The deferred robustness items (a `meta.json` without `log_records`, no fsync of the restart generations, the worker orphan window) go to a later sub-project and are listed as known limitations in the release notes.
5. **Approach:** a static version in one place plus a hatchling build hook that writes the build stamp into the wheel (approach A; not hatch-vcs, not a release script).

## 1. Why

`gqteashmd` is at `0.1.0.dev0`, has no tags, and runs as an editable install from the repository. Provenance records the git commit only because the package is imported from a git checkout (`provenance._git` looks for `.git` three levels above the module). A normal install records `git_commit: null`, so a project run from it cannot be traced back to the code. That is the "build stamp" deferred to the release since P3c.

A release gives one named, tested state of the code (all sub-projects through the censored analysis), with the exact environment it was tested in and the evidence that a clean install works. Later work (the parked analysis change, the robustness items) builds on it.

The version is in no stage fingerprint (it is written only to `provenance.json` and to the `gqteashmd_version` attribute of the HDF5 files), so moving from `0.1.0.dev0` to `0.1.0` makes no project stale.

## 2. The version and the build stamp

### 2.1 One source for the version

- `src/gqteashmd/__init__.py` holds `__version__`. The release commit sets it to `"0.1.0"`.
- `pyproject.toml`: `[project]` drops `version` and gets `dynamic = ["version"]`; new `[tool.hatch.version] path = "src/gqteashmd/__init__.py"`.
- After this change the development environment needs `pip install -e . --no-deps` once more (documented in `docs/development.md`).

### 2.2 The build hook

- New file `hatch_build.py` at the repository root, class `CustomBuildHook(BuildHookInterface)`, configured by `[tool.hatch.build.targets.wheel.hooks.custom]`.
- It acts on wheel builds only. For an editable build (hatchling passes `version == "editable"`) it does nothing; the editable install keeps using the live checkout (2.4).
- It runs `git rev-parse HEAD` and `git status --porcelain` in the build's root directory and writes a temporary file (outside the source tree) with exactly three assignments:
  ```python
  COMMIT = "<40-hex commit>"      # or None
  DIRTY = False                   # or True, or None
  BUILD_TIME = "<UTC ISO 8601, seconds>"
  ```
  and adds it to the wheel as `gqteashmd/_build.py` (`build_data["force_include"]`).
- Without git, or outside a git checkout, or if a git call fails: `COMMIT = None`, `DIRTY = None`; the build does not fail.
- The source tree is never written. `.gitignore` gets `src/gqteashmd/_build.py` as a guard.
- Only a wheel is built for the release; no sdist.
- `environment.yml` gets `hatchling>=1.24` (conda-forge), so the wheel can be built without build isolation and without downloading anything, and the lock file records the build backend.

### 2.3 Reading the stamp

New module `src/gqteashmd/build_info.py` (standard library only):

- `build_stamp() -> dict | None`: imports `gqteashmd._build` if it exists and returns `{"commit", "dirty", "build_time"}`; `None` when the package carries no `_build.py`.
- `commit_info() -> CommitInfo` (frozen dataclass `commit: str | None`, `dirty: bool | None`, `source: "git" | "build" | None`, `build_time: str | None`): the live checkout first (the logic of today's `provenance._git`, moved here), then the stamp, else all `None`.

### 2.4 Provenance

`collect_provenance()` takes its commit from `commit_info()`:

- `git_commit`, `git_dirty`: unchanged meaning, from the live checkout when there is one (as today), otherwise from the stamp.
- New `commit_source`: `"git"`, `"build"` or `null`.
- New `build_time`: the stamp's time when `commit_source == "build"`, else `null`.
- `provenance.json` `schema_version` stays 1 (fields are only added). A damaged file is still replaced by a fresh list.

### 2.5 `gqteashmd --version`

- Prints `gqteashmd 0.1.0 (commit 82e7d35)`: the first 7 hex digits; `, dirty` is appended when `dirty` is true; without a commit it stays `gqteashmd 0.1.0`.
- The commit is looked up only when `--version` is given (a custom `argparse` action), so no other command runs `git`.
- `import gqteashmd.cli` imports nothing new beyond `gqteashmd.build_info` (standard library only); it still must not import pyscf, geometric, h5py or scipy.

### 2.6 What does not change

No stage, stage version, input key, output format, fingerprint or exit code changes. The golden test and every existing test stay as they are.

### 2.7 Tests

- `build_stamp()` with and without a `_build.py` (a stub module injected in `tmp_path`/`sys.modules`).
- `commit_info()` and the provenance fields for all three sources (checkout, stamp, neither).
- The `--version` text for a clean commit, a dirty one and none.
- The hook: a wheel built into `tmp_path` from a temporary clone contains `gqteashmd/_build.py` with that clone's commit and `DIRTY = False`; an editable build gets no stamp. Marked `slow` (a real build).
- `import gqteashmd.cli` still does not import pyscf, geometric, h5py or scipy (the existing test).
- New tests are checked with `OPENBLAS_CORETYPE=SandyBridge` and count a zombie as ended where they check processes (CLAUDE.md rules).

## 3. The lock file

- `environment.lock.txt`: `conda list --explicit --md5` of `gqteashmd-dev` after the full suite has passed in it on the release branch (step 5.3). linux-64 only; the file says so in its header comment.
- `environment.yml` stays the loose development spec and is what CI installs. So CI tests the loose spec; the full suite and the clean-install check test the locked one.
- The gate fails if a runtime dependency (`pydantic`, `numpy`, `scipy`, `pyscf`, `h5py`, `geometric`) of the locked environment was installed by pip rather than conda (`conda list` channel `pypi`), because the lock would not capture it.

## 5. The gate and the release steps

### 5.1 The clean-install check

`tools/release/clean_install_check.sh VERSION`, run in WSL from the repository. Every check is fixed here; the script exits non-zero and prints FAIL at the first failing one.

1. `VERSION` equals `__version__` at HEAD, and the working tree is clean.
2. HEAD is cloned into `~/release_check/<VERSION>/src` (outside OneDrive and `/mnt/c`), and the wheel is built there with `pip wheel . --no-deps --no-build-isolation -w ~/release_check/<VERSION>/dist`, using `gqteashmd-dev`'s hatchling.
3. A fresh environment `~/release_check/<VERSION>/env` is created from `environment.lock.txt` (`conda create --file`), and the wheel is installed into it with `pip install --no-deps`. No runtime dependency there comes from pip (section 3).
4. From a directory outside the repository, `gqteashmd --version` prints exactly `gqteashmd <VERSION> (commit <first 7 of HEAD>)`.
5. `gqteashmd run tools/release/water_check.toml` with the project in `~/release_check/<VERSION>/project` exits 0; `07_analysis/analysis.json` exists; the last `provenance.json` entry has `gqteashmd == VERSION`, `commit_source == "build"`, `git_commit == HEAD` (40 hex) and `git_dirty == false`.
6. `~/release_check/<VERSION>/report.json` records every check with its value; the script prints PASS.

`tools/release/water_check.toml` is water CIS/STO-3G at the size of the end-to-end dynamics test (`tests/test_e2e_dynamics.py`: its sampling, selection and `[dynamics]` settings), through the analysis. A fast test checks that `gqteashmd validate` accepts it.

### 5.2 Privacy of the release files

The GitHub Release carries only the wheel and `environment.lock.txt`. The wheel's stamp holds a commit and a time; the lock file holds package URLs. `report.json` and the project directory (paths with the user name, the host name in `provenance.json`) stay local and are not attached.

### 5.3 The steps

1. On `feat/release-0.1.0`, one commit per task: the version source, the build hook, `build_info`, provenance and `--version`; the gate script and `water_check.toml`; the documents and `CHANGELOG.md` (dated at step 8).
2. The final review and its fix wave.
3. On the branch head: CI green, and the full suite `pytest -W error` here with SHARC and ORCA, in `gqteashmd-dev` (with hatchling added).
4. `environment.lock.txt` exported from that environment and committed. That commit changes only the lock file, so no gate is rerun.
5. The owner decides the merge into `main` (local, `--no-ff`); `main` is pushed and CI runs on it.
6. The clean-install check on the merge commit: PASS.
7. The annotated tag `v0.1.0` on that commit (from WSL); the owner's OK to push the tag.
8. `CHANGELOG.md`'s date is the tag's; if the date written at step 1 differs, it is corrected in the bump commit of step 10 (the tag is not moved).
9. The owner creates the GitHub Release on github.com from the tag (the `gh` CLI is not installed, and the session does not use the owner's GitHub login), with the CHANGELOG entry as text and the wheel and lock file as assets. A local folder `~/release_check/0.1.0/upload/` holds exactly those three files.
10. `main` is bumped to `0.2.0.dev0`, CLAUDE.md records the release, and both are pushed.

A failure of CI, the full suite or the clean-install check stops the sequence; the cause is fixed on the branch (or, after the merge, on a `fix/` branch merged by the owner) and that gate is rerun. Nothing is tagged before step 6 passes.

## 6. Out of scope

- PyPI, conda-forge, an sdist, Zenodo or `CITATION.cff` (decision 1).
- Any behaviour change, including the deferred robustness items and the parked analysis change (decision 4).
- Bumping the Node.js 20 actions in CI (informational warning only).
- A lock file for other platforms (Linux only).

## 7. Risks

- **The hook runs inside an isolated or unusual build** (for example a build from a copied tree without `.git`): the stamp then says `commit = None`, and the clean-install check fails at step 4 or 5 rather than releasing an untraceable wheel.
- **The locked environment cannot be recreated** (a package removed from conda-forge): `conda create --file` fails at gate step 3, and the release waits.
- **The full suite fails for an existing, known reason** (the flaky live-SHARC test, CLAUDE.md 3a): treated as a failure; a rerun of that test alone is recorded, and the owner decides whether it blocks.
